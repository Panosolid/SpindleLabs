# Sketches, features, the timeline and undo

How Design's document fits together, decided before step 21b saves the first sketch (design check, 2026-10-17), so that undo (step 20), the file format (docs/project-format.md) and the timeline (step 24) never need a rewrite. Fusion 360 is the reference for behaviour; where we are unsure how it behaves, we ask the owner, who has it.

## 1. The document is an ordered recipe; geometry is never stored

- Design's data is a list of timeline items in build order: sketches, features (extrude, box, later revolve, fillet…), and later construction planes. A sketch is a timeline item of its own, as in Fusion ("Sketch 1", then "Extrude 1"), not a separate unordered list: a sketch on a face (26) must come after the feature that made the face, and the extrude that uses it after that, so order is part of the data.
- Every item stores its intent (what the user asked for), never the geometry it produced. Bodies, faces, sketch outlines and profiles are worked out by replaying the list through the kernel. A cache of results (58) lives only in memory, keyed by the inputs that made it; it is never written to the file and never trusted over a rebuild.
- Big data that is not a recipe (an image's pixels, an imported mesh or STEP file) goes into the project as a blob referenced by a content hash, not inline in the JSON, once such data is saved. This keeps undo snapshots (section 4) small.

## 2. Ids

- Every timeline item, sketch point and sketch curve has an id that is unique in the document and never reused, even after the thing is deleted. Ids come from a counter stored in the document (`nextId`): `sketch-2`, `point-3`, `line-4`, `feature-5`. Taking "the largest id + 1" instead would hand a deleted item's id to a new one, and a link, selection or AI command naming the old one would silently point at the new one.
- Ids are never list positions. Names people read ("Sketch 1", "Extrude 2") are numbered by position at display time and are not ids.
- A merge of two documents (remix updates, X12/C4) renumbers the incoming side's new ids; nothing else ever changes an id.
- Topological naming (24, 40) builds on these ids: a face made by an extrude is named from the feature id and the id of the sketch curve it was swept from ("feature-5 / side of line-4"), so sketch curves need stable ids from the first saved sketch (21b).

## 3. Sketches

- A sketch item's intent is `{ type: "sketch", parameters: { plane } }`. `plane` is a reference, not coordinates: `"XY"`, `"XZ"`, `"YZ"` for the origin planes (21), a stable face id from 24 for a sketch on a face (26), a construction plane's id later (60). The plane's position is worked out on replay, so a sketch follows its face when an earlier feature changes.
- The sketch's content sits in Design's `sketches` list under the same id: `points` (`{ id, x, y }`, in mm, in the sketch plane's own 2D frame, never world coordinates), `curves` (`{ id, kind: "line", start, end }` naming point ids; circles `{ id, kind: "circle", centre, radius }` round a point id, radius in mm, from 22b; arcs `{ id, kind: "arc", start, end, centre }`, counter-clockwise round the centre from start to end, three point ids, from 23a) and `constraints` (empty until 47). Lines drawn in a chain share their end points, so "coincident" is already true in the data when the solver arrives.
- Profiles are never stored. The kernel finds a sketch's closed outline (21a, `sketch_outline`) or regions (48) on replay.
- A feature refers to what it uses by id: an extrude of a sketch is `{ type: "extrude", parameters: { sketch: "sketch-2", distance: 10 } }` with `dependsOn: ["sketch-2"]`. Until 48 a sketch has one closed outline and that is what is extruded. From 48 a `region` parameter names the region by the ids of the curves around it (exact form decided at 48), never by an index, so adding a line elsewhere in the sketch never makes an extrude pick a different region.

## 4. Undo stays whole-document snapshots, for good

- Undo (20) keeps the project as text after each step. That stays: it is not replaced by "undo this timeline edit" at 24. Every timeline edit (add, edit, delete, reorder, suppress, move the rollback marker, draw a line in a sketch) already is one recorded step, so snapshot undo is timeline undo, and it is correct for every kind of change without writing an inverse for each command (a source of bugs). The same goes for ownership hand-overs and accepted AI commands, which already undo as one step each.
- Because the document holds only intent, a snapshot is kilobytes; 100 steps is a few megabytes at most. If a project's text ever passes about 1 MB, the history keeps each workspace's part separately and shares parts that did not change; the interface stays the same.
- Undo rebuilds by replaying the restored recipe. With the result cache (58), returning to an earlier recipe finds its results already cached, so undo stays instant on big parts.
- An AI preview (A2) is the same mechanism: apply the commands to a copy of the document, replay it, draw the result ghosted; Accept is one `history.step`. It does not need to wait for 51.

## 5. Replay

- Design's rebuild walks the timeline in order up to the rollback marker, skipping suppressed items. Each item is one pure kernel operation with explicit inputs (the resolved plane, the outline, earlier bodies, and the item and curve ids for naming); the kernel never reads the project file. A failing item records its error and the items after it that depend on it are marked failed (57 shows them on the timeline); nothing throws past the rebuild.
- The rollback marker is stored in the document (`timeline.marker`: the id of the last item built, absent for "all"), as Fusion saves it with the design, so moving it is an undo step.
- An item can never be moved before something it depends on (its `dependsOn`, its sketch plane's feature); the reorder is refused with a message.
- Until 24 there is one body: the last solid feature's. Step 24 builds every solid feature, gives each its own body ("New body", as Fusion's first extrude) until joins and cuts arrive with booleans (35, 39), turns the box, cylinder and sphere presets into ordinary features inserted from the toolbar, and keeps the ready-made profiles as example sketches.

## 8. Names through booleans (step 34a)

Written before any Design code for booleans (the kernel repo's `docs/progress/booleans.md`, 34a), so Combine (35f), Extrude join and cut (39) and fillets (44–46) never need a rename. Until now a name belongs to one feature; a boolean mixes features, so these rules say which features' faces a name comes from. The exact model that answers them, the oracle for Design from 35e, is `packages/testing/src/boolean-naming-model.ts` (34a2 onward). Where a rule says "earliest", the order is the timeline's.

- Bodies (rule 1). A body has an id of its own, `body:<the feature that first made it>`, separate from that feature's id (a body outlives the feature that made it, and one feature can leave several bodies). A join or cut that changes a body keeps its id; a Combine's tool bodies are used up (gone) unless Keep tools is on, and then they stay exactly as they were. A body's number people read ("Body 3") is given once, when it first appears, and stored (35e).
- One feature, one renaming. A feature's names are judged on the bodies just before it against the bodies just after it. Combine applies its tools one at a time in the order picked (that decides the shape), but it renames once.
- A cut or intersect that leaves a body in pieces (connected solids; a piece may hold a void). Walk the body's faces as they were before the feature, in made order: by the feature that made each face (its first name), then that feature's own order (an extrude: start cap, end cap, then the sides in the outline's order; a box: bottom, top, front, back, left, right; a cylinder: bottom, top, side; a sphere: lower, upper). The piece holding the first face whose surviving part (what is still on the result's surface under that face's name) is not empty and lies wholly in that one piece keeps the body's id, whatever its size (Ben's Fusion check F1: a 100 × 20 × 10 bar cut by a slot at x 30–40; the caps and the long sides are split, the side from the rectangle's second line, x = 100, is the first face wholly in one piece, so the far piece keeps Body1, even when made the smaller one). Every piece is ranked by the first face in that walk reaching it, then by its share of that face's area (larger first), then by volume (larger first), then by its lowest corner (smaller x, then y, then z): a piece no face reaches comes after every piece one does. When no face lies wholly in one piece (a body cut into four by two crossing slots), the first piece by rank keeps the id. Every other piece gets a new id, `body:<the feature that split it>/piece:<k>`, k counting from 1 in rank order.
- A cut or intersect that would leave nothing of a body fails with words, and every body stays as it was (Fusion check F3). A result whose pieces touch only along an edge or at a corner fails with `NonManifoldResult` (B0 decision 2). Both are the feature failing, not a rename.
- Joins. A Combine join: the piece holding the target keeps its id, and any piece of tool left apart from it is a new body numbered as above (Fusion check F2: Body1 and a new Body3, no warning). An Extrude join (39) touching bodies that already existed: each result piece holding any of them keeps the id of the earliest-made of them (Fusion check F6, queued; the rule stands until it answers), the others' ids are gone, and a piece holding only the new extrude is `body:<the extrude>`. Earliest-made: by the feature in the id, then `body:F` before `body:F/piece:1` before `body:F/piece:2`.
- Faces (rule 2). A face keeps the name of the input face it lies on, whichever feature made that face (a hole's wall is the cut tool's side, `face:feature-3/side:circle-5`), and keeps it when only its outline changes: a sketch on it keeps its plane until the face's surface itself moves (Fusion check F5).
- Merged faces (rule 4). Faces of the inputs that end up as one face (two blocks joined flush: their tops in one plane, touching) make one face answering to every name it had. The name shown is the first: the target's names first (the earliest participant's for an Extrude join), then each tool's in the order picked, each body's in made order.
- Split faces (rule 3). When two or more faces carry the same name (a cap cut in two, even when the two pieces went to two bodies), each of those pieces adds a tag: the sorted shown names of the faces bordering it that border none of the other pieces (normally the walls of what cut it; the F1 bar's far top piece is tagged with the bar's x = 100 side and the slot's x = 40 wall). The name with its tag is written `face:feature-2/end#face:feature-2/side:line-2,face:feature-4/side:line-4`. Pieces whose tags are the same share the name and are never guessed between (the 25a4 path: the reference says its face is ambiguous). A reference made while its face was whole and finding it split later goes to the piece holding the sketch's origin, else the largest by area (a tie: ambiguous), always with a warning (Ben's rule). A reference holding a tag finds the one piece with that tag; when the face is whole again it finds the whole face.
- Edges (rule 5). An edge is named by its two faces' names (each the shown name with its tag if it has one), sorted: `edge:face:feature-2/end+face:feature-4/side:line-4`. When the same two faces meet more than once, the sorted shown names of the other faces meeting at its two ends are added, `;ends:face:feature-2/start,face:feature-4/start`; when they still don't tell the edges apart, two sides of one extrude's outline fall back on step 27b's corner names (which end of each side's curve), and anything else is shared and never guessed.
- Old names (rule 6). Every name written up to now still resolves exactly as before. A face name is unchanged (`face:feature-7/side:line-4`): the new form only adds a tag. An old edge name holds one feature, `edge:feature-7/side:line-4+start`, and reads as the edge between `face:feature-7/side:line-4` and `face:feature-7/start`; an old ordered name, `edge:feature-7/side:line-4>side:arc-6`, reads as the 27b corner it always named. New edge names start `edge:face:`, so the two forms never read the same. Ids inside names stay written with encodeURIComponent (`naming.ts`), so the separators `/ : + > # , ;` can never come from an id.
- The Combine feature (rule 7, built at 35f). `{ type: "combine", parameters: { target: "body:feature-2", tools: ["body:feature-5"], operation: "join" | "cut" | "intersect", keepTools: false } }`, tools in the order picked, `dependsOn` the features named by those bodies' ids. Its bodies are fixed when it is made, by id: a body made later is never added (Fusion check F4). An Extrude gains `operation` (`new`, `join`, `cut`, `intersect`) and its participants, `bodies`, the same way at 39.
